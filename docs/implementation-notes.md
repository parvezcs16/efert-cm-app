# Implementation Notes

Assumptions made where requirements were ambiguous, per AGENTS.md's change
discipline (documented here instead of guessed silently).

## Recurring gotcha: Alembic + Postgres native enums

Every model column typed as a Python `enum.Enum` becomes a native Postgres
`CREATE TYPE ... AS ENUM`. Alembic's autogenerated `downgrade()` drops the
*tables* but never the enum *types*, so a downgrade followed by a re-upgrade
fails with `type "..." already exists`. After every `alembic revision
--autogenerate` that adds/removes enum columns, manually add
`sa.Enum(name='...').drop(op.get_bind(), checkfirst=True)` calls at the end
of `downgrade()` for each enum type the migration's `upgrade()` created.

## Phase 2 - Authentication

- **P-Number format**: no format was specified, so it's validated as
  `^[A-Za-z0-9-]{3,20}$` (alphanumeric plus hyphen, 3-20 chars). Revisit if
  the organization has a fixed P-Number scheme.
- **Password policy**: minimum 8 characters, at least one letter and one
  digit. No complexity requirements beyond that.
- **Registration approval / admin employee creation authority**: restricted
  to `SYSTEM_MANAGER` and `SYSTEM_ADMINISTRATOR` roles. requirements.md
  groups this under a generic "Management" actor without naming a specific
  role; these two were chosen as the closest fit to HR/account-administration
  authority. Revisit if `LOCATION_MANAGER` or `FINANCE_ADMIN` should also
  have this.
- **RBAC model**: a single `role` enum per employee (`EMPLOYEE`, `SERVER`,
  `KITCHEN_OPERATOR`, `LOCATION_MANAGER`, `SYSTEM_MANAGER`, `FINANCE_ADMIN`,
  `SYSTEM_ADMINISTRATOR`), not multi-role. Simpler than a many-to-many
  roles table; revisit if an employee genuinely needs more than one role
  concurrently (e.g. a server who is also a kitchen operator).
- **Temporary password delivery**: on registration approval or admin
  creation, the temporary password is both emailed to the employee (via the
  notification abstraction) and returned in the admin-facing API response.
  Returning it in the response is a dev/ops convenience; reconsider for
  production if the API response itself is considered a leakage surface.
- **OTP tuning**: 6-digit codes, 5 minute expiry, 5 max attempts per code,
  60s resend cooldown -- all configurable via env vars
  (`OTP_TTL_SECONDS`, `OTP_MAX_ATTEMPTS`, `OTP_RESEND_COOLDOWN_SECONDS`).
- **Login lockout**: 5 consecutive failed attempts locks the account for 15
  minutes (`LOGIN_MAX_ATTEMPTS`, `LOGIN_LOCKOUT_MINUTES`). Not specified in
  the docs; standard industry defaults were used.
- **Tokens**: short-lived JWT access token (15 min) + opaque, DB-backed,
  rotating refresh token (30 days, single-use -- reuse of an already-rotated
  token is treated as a signal of theft and rejected). No refresh-token
  family-wide revocation on reuse detection yet (only the reused token
  itself is rejected); consider adding if this becomes a real threat model
  concern.
- **Notifications**: only a minimal `NotificationSender` port + a
  console/log-based email adapter exist so far (needed now because OTP
  delivery is core to this phase). Real provider integration, templates,
  and statement-frequency scheduling are still Phase 9.
- **Login step-up OTP**: `OtpPurpose.LOGIN_STEP_UP` exists in the enum for
  forward compatibility (docs mention conditional step-up authentication)
  but no endpoint uses it yet -- there's no concrete policy yet for when
  step-up should trigger.

## Phase 3 - Locations and Menu

- **Manager-eligible roles**: only `LOCATION_MANAGER`, `SYSTEM_MANAGER`, and
  `SYSTEM_ADMINISTRATOR` employees can be assigned as a `Location.manager`.
- **MenuCategory is location-scoped** (per docs/database.md's explicit
  `location_id` field on it): each location curates and orders its own
  category list, rather than categories being a shared global taxonomy.
- **MenuItem's category assignment is organizational, not restrictive**:
  `MenuItem.category_id` records where it's catalogued, but
  `MenuItemLocation` (not the category) is what actually controls which
  locations can sell an item, at what price. This reconciles MenuItem
  having a single `category_id` while `MenuItemLocation` exists as a
  separate per-location join table in the documented schema.
- **MenuItemLocation is current-state, not a price history ledger**: one
  row per (item, location) via a unique constraint, with `effective_from`/
  `effective_to` supporting a single scheduled window (e.g. an upcoming
  price change). Full point-in-time price history isn't built -- the
  actual immutable historical record is the price snapshot each OrderItem
  captures at order time (Phase 4), consistent with CLAUDE.md.

## Phase 4 - Employee Ordering

- **Employee-only for now**: `CustomerType.GUEST` exists in the enum and
  `Order.employee_id` is nullable for forward compatibility, but the API
  only ever creates `CustomerType.EMPLOYEE` orders. Guest ordering is
  Phase 6, which will also add `guest_session_id` (not present yet -- no
  `guest_sessions` table exists to reference).
- **Prices hidden from employees in the ordering UX**: menu browsing and
  order responses omit `unit_price` for the employee actor, per CLAUDE.md
  ("never expose internal prices... unless explicitly required"). Employees
  will see what they were charged via the mess ledger in Phase 8, not
  inline in order history.
- **`OrderItem.kitchen_station_id` is nullable and left unset by Phase 4.**
  Routing an item to a specific kitchen station is a queue/kitchen concern
  owned by Phase 5; no routing rule exists yet to auto-assign it.
- **Order status progression beyond creation/cancellation is out of scope
  here.** Phase 4 only ever produces `PENDING` orders and allows the owning
  employee to cancel (any status before `SERVED`). The
  `CONFIRMED -> QUEUED -> PREPARING -> READY -> SERVED` progression is
  Phase 5 (kitchen) and Phase 7 (booking ingredient-confirmation) territory.
- **Order numbers**: a single global Postgres sequence (`order_number_seq`,
  formatted `ORD-000001`), not per-location or per-day. Nothing in the docs
  specifies a numbering scheme.
- **Booking validation**: `scheduled_for` must be strictly in the future.
  The "two-hour threshold" business rule for management to confirm
  ingredients (docs/business-rules.md) is a Phase 7 concern, not enforced
  at booking time here.

## Phase 5 - Kitchen

- **Kitchen/server roles are not location-scoped**, unlike `LOCATION_MANAGER`.
  The Employee model (Phase 2) has no "home location" field for SERVER or
  KITCHEN_OPERATOR staff -- only `Location.manager_id` ties one employee to
  one location. So `require_kitchen_staff` is a plain role check
  (SERVER, KITCHEN_OPERATOR, LOCATION_MANAGER, SYSTEM_MANAGER,
  SYSTEM_ADMINISTRATOR) that lets any employee with one of those roles act
  on kitchen operations at *any* location. Revisit if per-location staff
  assignment is ever added.
- **Order status stays order-level, not per-item**, matching
  docs/database.md (only `Order` has a `status` column; `OrderItem` only
  has `kitchen_station_id`). A kitchen station's queue view is therefore
  "orders with at least one item routed to this station and status in
  {QUEUED, PREPARING}" -- imprecise for an order whose items span multiple
  stations at different readiness, but faithful to the documented schema.
  A genuinely per-item kitchen status would be a bigger schema change --
  revisit if multi-station orders turn out to need finer-grained tracking.
- **Queuing requires every item to have a station assignment** in one call
  (`POST /orders/{id}/queue` with a full `{order_item_id: station_id}`
  map) -- partial/incremental routing isn't supported.
- **Booked-order ingredient confirmation is NOT gated here.** Any order
  (including BOOK_FOR_LATER) can move PENDING -> CONFIRMED -> QUEUED
  through this phase's plain transitions; the "verify ingredients, alert
  the manager if unavailable" gate from docs/kitchen.md is Phase 7's job
  and will need to wrap/extend the `confirm`/`queue` transitions for
  booked orders specifically.
- **"Serve directly" is available to all kitchen-staff roles**, not
  SERVER-only, since docs/kitchen.md says only "authorized servers" without
  defining who else may be authorized.
- **WebSocket broadcasting is single-process/in-memory**
  (`ConnectionManager` in app/websocket/manager.py) -- correct for one
  worker, but would need a shared pub/sub (e.g. Redis) if the app is ever
  run with multiple worker processes, since a status change on worker A
  wouldn't reach a kitchen display connected to worker B.
- **Kitchen WebSocket auth**: the access token travels as a `?token=`
  query parameter (`/ws/kitchen/{location_id}?token=...`) since browsers
  can't set an Authorization header during a WebSocket handshake.

## Phase 6 - Guests

- **"Signed" QR token implemented as opaque bearer + server-side hash
  lookup**, not a JWT. docs/guest-management.md says "use a signed,
  non-guessable temporary token" but also "the QR should identify a
  server-side guest session" -- the latter implies stateful lookup
  (needed to make it trivially revocable for close/reopen/expiry), so the
  same pattern as RefreshToken was reused: `secrets.token_urlsafe(32)`,
  SHA-256 hash stored, shown once.
- **Guest access token is separate from the QR token**: `/guest/auth`
  exchanges the long-lived (24h) QR token for a short-lived (2h) JWT
  (`typ: guest_session`) that guest-ordering endpoints accept as a Bearer
  token. This mirrors the employee refresh-token/access-token split.
- **Any active employee may open a session for any previously-registered
  guest**, not just the guest's original registering host -- per "a
  different employee brings the same previously-registered guest" --
  becoming that session's `host_employee_id`. Closing/reopening a session
  is restricted to that specific session's host (not the guest's original
  registering host, which may differ).
- **The 24h token-validity window is fixed at session creation** and is
  NOT extended by closing/reopening -- closing only changes `status`, per
  "QR access does not immediately become invalid on close... fully
  invalidated after 24 hours." A session whose token has expired can no
  longer be reopened.
- **All `/guest/*` portal endpoints require the session to be currently
  ACTIVE**, re-checked live against the DB on every request (not cached
  from the JWT) -- including read-only order history. docs only says
  closing "prevents normal continued ordering," so blocking history reads
  too is a conservative simplification, not a strict requirement; revisit
  if guests need to see past orders after their host closes the visit.
- **`/guest/auth` itself does not require an ACTIVE session** (only that
  the token hasn't hit its 24h expiry) -- a closed session can still be
  identified/re-authenticated; it's the subsequent ordering action that's
  blocked.
- **No guest-order cancellation** was added (not explicitly listed under
  Phase 6's bullets); only employee order cancellation exists (Phase 4).
- **Employee-facing price hiding extended to guests too**: guest order
  responses reuse the same price-free `OrderRead`/`OrderItemRead` schemas
  as employees. Nothing in the docs says guests must see prices, and since
  PRIVATE guest costs are charged to the host's ledger (not the guest),
  treating the whole ordering UX as price-hidden by default seemed the
  safer default -- revisit if OFFICIAL guests specifically should see
  pricing.
- **Guest.host_employee_id vs GuestSession.host_employee_id**: the Guest
  record's field is who originally registered them; each session
  independently records who is hosting that particular visit -- these can
  differ (see above).

## Phase 7 - Booked Order Management

- **Ingredient confirmation is a separate concept from the generic
  `OrderStatus`**: a new `ingredient_status` (PENDING/CONFIRMED/DELAYED,
  null for non-booked orders) gates `KitchenService.confirm()` for
  BOOK_FOR_LATER orders specifically. This is the "hook" anticipated in
  the Phase 5 notes -- once ingredients are CONFIRMED, a booked order goes
  through the exact same confirm/queue pipeline as any other order, which
  satisfies the "queue release" bullet without a separate release action.
- **Who reviews ingredients**: gated by the same `require_kitchen_staff`
  role check as other kitchen actions (SERVER, KITCHEN_OPERATOR,
  LOCATION_MANAGER, SYSTEM_MANAGER, SYSTEM_ADMINISTRATOR), not restricted
  to "system manager" specifically, since docs/kitchen.md says generically
  "manager reviews the order."
- **No automatic/scheduled re-alerting near the 2-hour threshold.**
  "The booking workflow must allow management to verify ingredients before
  the two-hour threshold" (CLAUDE.md) is read as a capability requirement
  (nothing blocks review at any time before then), not a requirement to
  proactively re-notify as the deadline approaches -- that would need a
  background scheduler (the empty `app/workers/` module would be the
  natural home for it) which doesn't exist yet.
- **The "manager alert/bell" reuses the existing kitchen WebSocket
  channel** (`/ws/kitchen/{location_id}`) with a distinct message type
  (`booking.alert`) fired immediately on booked-order creation, rather
  than a separate manager-specific channel -- anyone connected to that
  location's kitchen feed (which already includes all kitchen-staff
  roles) sees it; the "prominent animated bell" itself is a frontend
  concern.
- **Guests have no email** (docs/database.md's Guest entity has none), so
  a booking update for a guest order notifies that session's host employee
  instead of the guest directly.
- **Delay validation**: `new_scheduled_for` must be in the future, same
  rule as the original booking. Re-delaying an already-DELAYED order is
  allowed (treated the same as PENDING for gating purposes); delaying an
  already-CONFIRMED order is not.

## Phase 8 - Consumption and Billing

- **Served quantity defaults to ordered quantity at serve time.** Nothing
  in the docs says otherwise, and the server marking an order SERVED is
  read as attesting the full order was handed over; a shortfall is
  corrected afterwards via the request/validate flow, not guessed at
  serve time.
- **ConsumptionRecord is one row per OrderItem** holding both the current
  validated state and (while pending) the requested correction inline --
  not a separate correction-request table. The audit trail for "actor,
  original qty, corrected qty, reason, timestamp" (docs/consumption.md)
  comes from AuditLog entries, not from history on this row.
- **Only one pending correction at a time per item**: requesting again
  while `status=CORRECTION_REQUESTED` is rejected (422) until a server
  validates (approves or rejects) the existing request.
- **Correction requests are employee-order-only.** "Employee may
  request/change served quantity" (CLAUDE.md) names the employee
  specifically; there's no guest-initiated correction endpoint (guests
  have no account to make the request from anyway).
- **A correction posts exactly one net adjustment entry** for the quantity
  delta (CREDIT if reduced, DEBIT if increased), referencing the original
  charge via `reversal_of_id` -- not a reversal-then-recharge pair. The
  original DEBIT entry is never modified.
- **LedgerSourceType is preserved across corrections**: an adjustment
  entry keeps the same source_type as the charge it corrects (identified
  as a correction via non-null `reversal_of_id`, not via a separate
  "ADJUSTMENT" source_type) -- otherwise filtering "personal bill" vs
  "private guest bill" by source_type would silently drop its corrections
  into an undifferentiated bucket.
- **Ledger accounts are get-or-create, not pre-provisioned**: an
  employee's personal account and a location's official account are
  created lazily on first use. One EMPLOYEE_PERSONAL account per employee
  (global, not per-location) and one OFFICIAL account per location
  (docs/billing.md "Accounts"); enforced via unique constraints.
- **Private guest billing follows the session's host, not the guest's
  original registering host** (see Phase 6 notes) -- consistent with who
  actually brought the guest on that visit.
- **"Official guest billing where permitted"**: gated by the same
  `require_location_authority` dependency as other location-management
  actions (LOCATION_MANAGER for their own location, SYSTEM_MANAGER/
  SYSTEM_ADMINISTRATOR for any) -- not FINANCE_ADMIN-specific, since the
  docs don't name a specific role.
- **Statement generation vs. statement scheduling split across phases**:
  Phase 8 adds the employee's `statement_frequency` preference and
  on-demand statement views computed directly from LedgerEntry rows
  (docs/billing.md: "based on ledger transactions, not mutable order
  state"). It does NOT build the automated periodic generation/email
  delivery job -- that's Phase 9's "statement schedules" (notifications),
  which doesn't exist yet (no scheduler/worker infrastructure is wired up).

## Phase 9 - Reviews and Notifications

- **Review structure**: one `Review` row per submission (overall rating +
  optional comment), with per-category ratings in a child
  `ReviewCategoryRating` table -- not one Review row per category. This
  matches docs/database.md's single "rating/comment" pair on Review while
  still supporting multiple category ratings per submission.
- **ReviewCategory names are immutable once created** -- no rename
  endpoint. "Keep review configuration versioned enough that historical
  reviews remain interpretable when questions change" (docs/reviews.md) is
  satisfied by disabling a category and adding a new one instead of
  editing in place, so a rating's category FK never points to something
  that changed meaning after the fact.
- **Reviews are employee-only** (no guest review endpoint) -- docs frame
  review privacy specifically around "employee chooses whether a review is
  anonymous," and guests have no account to attach a review history to.
- **Anonymity masking happens in the read schema** (`ReviewRead`), applied
  uniformly to every viewer (including the reviewer's own "my reviews"
  list) rather than only "management screens" specifically, since docs
  don't define a separate privileged-vs-peer visibility tier.
- **An ORDER review requires the order to be SERVED and owned by the
  reviewing employee.** Not explicitly stated in the docs, but "individual
  order review" implies reviewing something you actually received.
- **Category management is system-role-only** for both global
  (`location_id=None`) and location-specific categories -- toggling
  `enabled` doesn't reuse `require_location_authority` for
  LOCATION_MANAGER, to avoid needing to resolve a category's location
  before authorizing. Revisit if per-location managers need this.
- **Notification persistence**: all existing email call sites (OTP codes,
  registration approval, admin-created employee credentials, booking
  confirm/delay) were migrated from calling the raw `NotificationSender`
  to `NotificationDispatchService`, which additionally writes a
  `Notification` row per attempt (SENT/FAILED) -- fulfilling
  docs/database.md's `Notification` entity, which until now existed only
  as a documented schema, not actual persisted history.
- **Statement scheduling is a single in-process asyncio loop**
  (`app/workers/statement_scheduler.py`, started from `app.main`'s
  lifespan), checking hourly for employees whose
  `Employee.next_statement_due_at` has passed. No external scheduler/queue
  (Celery, APScheduler, Redis) was introduced -- consistent with the
  kitchen WebSocket manager's same single-process limitation, documented
  there in the Phase 5 notes. `next_statement_due_at` is set on activation
  and recomputed whenever the employee changes their frequency preference;
  MONTHLY is treated as a fixed 30-day interval, not a calendar month.
- **Statement email body is plain text**, built directly from ledger
  entries in the due period (personal + private-guest only, matching the
  consolidated billing view) -- no HTML template engine was introduced.

## Phase 10 - Reporting and Hardening

- **Scope split**: only "management reports," "reconciliation," "audit
  reports," and the missing "adjust/reverse billing" capability from
  requirements.md became application code. "Performance testing,"
  "backup/recovery," and "production deployment" are operational
  concerns, not code to write against a local dev checkout with no real
  deployment target -- see docs/operations.md instead of looking for them
  here.
- **Reconciliation is a verification report, not a repair tool.** It
  flags served items whose billed amount doesn't match
  `served_quantity * unit_price`; fixing a flagged mismatch (which
  shouldn't occur under normal operation -- ConsumptionService and
  LedgerService always keep the two in lockstep) is a manual step via the
  new billing-adjustment endpoint, not automated.
- **Manual billing adjustments reuse `LedgerSourceType` rather than adding
  a dedicated "ADJUSTMENT" value**: the caller picks PERSONAL_CONSUMPTION
  or PRIVATE_GUEST for an employee account (OFFICIAL_GUEST is rejected
  there), or the endpoint fixes it to OFFICIAL_GUEST for a location
  account -- consistent with Phase 8's decision to keep corrections
  filterable by source_type rather than sorting them into a separate
  bucket.
- **New role usage**: `EmployeeRole.FINANCE_ADMIN` (defined since Phase 2
  but unused until now) gates employee-account billing adjustments
  alongside SYSTEM_MANAGER/SYSTEM_ADMINISTRATOR
  (`require_billing_admin`). Official-account adjustments reuse
  `require_location_authority` instead, for consistency with the existing
  official-bill-viewing endpoint.
- **Audit log query is SYSTEM_LEVEL_ROLES-only** (not
  `require_location_authority`), since `AuditLog` has no `location_id` to
  scope by -- a LOCATION_MANAGER cannot filter to "just their location"
  today. Revisit if that's needed later (would require tagging audit
  entries with a location where applicable).
- **Report/reconciliation windows default to a trailing 30 days** when
  `since`/`until` aren't supplied, rather than requiring both explicitly.
- **Reports are computed on demand, not cached or materialized** --
  acceptable at the data volumes a single mess/location produces; see
  docs/operations.md "Performance" for when to revisit.
- **Security hardening applied as part of this phase**: a production
  startup guard against the default `SECRET_KEY`, a non-root Docker user
  for the backend image, and nginx-level security headers + per-IP rate
  limiting on `/api/v1/auth/*`. Full rationale and what's deliberately
  left to infrastructure (TLS/HSTS, WAF, dependency scanning, secrets
  management) is in docs/operations.md, not duplicated here.

## Mobile app

- **Flutter, not React Native or a PWA** -- explicit choice by the project
  owner for a genuine native app. Built against the same `/api/v1` backend
  as the web frontend; no new API surface was needed except what the web
  frontend gaps had already surfaced (guest location/menu discovery,
  kitchen incoming-orders/pending-bookings -- see Phase 10 above).
- **Guest self-service stays on the web QR portal, not the native app.**
  `mobile/lib/core/api_client.dart` has no guest client at all. A host
  registers guests and opens sessions from the native app (mirroring
  `GuestsPage.tsx`), but the resulting QR still points at the deployed web
  app's `/guest?token=...` route (`ApiClient.webAppBaseUrl`, overridable via
  `--dart-define=WEB_APP_BASE_URL=...`), which guests open in their own
  phone browser. Rationale: guest QR access is inherently a one-off,
  no-install flow -- asking a guest to install an app defeats the point of
  a QR code, and the web portal already exists and works.
- **State management: `provider` + `ChangeNotifier`**, not Riverpod/Bloc --
  matches the app's actual complexity (one global `AuthController`, no
  cross-cutting state beyond auth) rather than adopting a heavier framework
  the app doesn't need.
- **Navigation: `go_router` with a `Drawer`, not a bottom nav bar.** Up to 7
  destinations (Order, My Orders, Guests, Billing, Reviews, plus
  role-gated Kitchen and Administration) don't fit a phone-width bottom bar
  legibly; a drawer mirrors `AppLayout.tsx`'s top nav without the width
  constraint. `GoRouter` is built once (`late final` in a `StatefulWidget`,
  not rebuilt from `context.watch` in a `StatelessWidget`) so auth-state
  changes re-run its `redirect` logic via `refreshListenable` instead of
  discarding navigation history.
- **Secure storage for tokens**: `flutter_secure_storage` (Android
  Keystore / iOS Keychain), not `shared_preferences`, since access+refresh
  tokens are long-lived bearer credentials -- same reasoning as the web
  frontend's choice of `localStorage` over an in-memory-only store, adapted
  to native platform keystores.
- **`API_BASE_URL` / `WEB_APP_BASE_URL` are compile-time `--dart-define`s**,
  not runtime settings -- there is no per-install configuration UI in
  scope; a deployed build is compiled once per environment, matching how
  the web frontend's Vite build bakes in its own API origin.
